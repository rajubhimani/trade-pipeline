# [done] Add Alembic for database schema migrations (postgres) — id: T-25

Added: 2026-07-27
Completed: 2026-07-27
Notes: Project currently manages the Postgres schema by hand (no migration tool). Add Alembic to formalize schema versioning — init alembic env, generate an initial revision matching the current schema, wire `alembic upgrade head` into startup/CI/Makefile. Implemented: `alembic.ini` + `migrations/` (env.py resolves DSN from `common/config.load_config()`, reuses a passed-in engine to avoid a second DB connection); hand-written `0001_initial_schema` revision matching `common/db_models.py` exactly (partition DDL stays in `common/partitioning.py`, outside Alembic, since it's a moving current/next-month target); `common/migrations.upgrade_to_head()` wired into `postgres_sink.init_schema` (used by both the consumer's own startup and the one-shot `migrate` compose service); `alembic` added to base deps (was previously only a transitive dagster dep) and `alembic.ini`/`migrations/` copied into the runtime Docker image; `make db-upgrade` / `make db-revision`. Verified against a live Postgres container: migration applies cleanly, schema matches the ORM models exactly, partitions still created correctly, full test suite (116 tests) passes unchanged. Follow-up: `tests/conftest.py`'s `pg_engine` fixture also switched from its own `Base.metadata.create_all` to `upgrade_to_head`, so tests now build the schema through the same Alembic path as prod instead of a second, independent one — no `create_all`/manual table creation left anywhere in the codebase. See `docs/DECISIONS.md` for full rationale.
