# Feature: Postgres range partitioning for the trades table

Status: shipped
Task: docs/tasks/completed/T-18-postgres-partitioning.md

## Problem / motivation

`trades` is an append-heavy, time-series table — every trade event ever processed lives in it forever.
At real scale this is exactly the case time-range partitioning exists for: it keeps each partition (and
its indexes) small regardless of total table size, and turns "delete old data" from a slow row-by-row
`DELETE` into an instant `DETACH PARTITION`. User asked directly whether the project should use
partitioning; the honest answer is yes, this is exactly the kind of table it's for.

## Scope

In: `Trade.__table_args__` (`common/db_models.py`) declares `postgresql_partition_by="RANGE
(timestamp)"` — a SQLAlchemy-native table option, confirmed via `CreateTable(...).compile(dialect=...)`
before relying on it. `common/partitioning.py` creates the actual child partitions (the ORM's
`create_all` emits the partitioned parent table but can't create children on its own): a `DEFAULT`
catch-all plus explicit monthly partitions for the current and next month. Wired into
`postgres_sink.init_schema()` so it runs automatically on every startup (idempotent — safe to call
every time).

Out: automatic partition rotation/pruning (dropping partitions older than N months) — a real
deployment would run this on a schedule (a natural fit for a Dagster asset, similar in shape to the
archival job), but isn't built here; tracked as a candidate follow-up.

## Design

- **Composite primary key `(id, timestamp)`, not just `id`**: Postgres requires every unique
  index/constraint on a partitioned table to include the partition key column — `id` alone as sole PK
  is rejected outright for a `PARTITION BY RANGE` table. `id` still self-populates via `Identity()`
  despite being part of a composite key — verified against a live Postgres container before relying on
  it (`GENERATED BY DEFAULT AS IDENTITY` works regardless of PK composition; plain `autoincrement=True`
  does not — that was an earlier, discarded approach).
- **`UniqueConstraint("broker_id", "trade_id", "timestamp")`**: same constraint, extended for the same
  reason. Doesn't meaningfully weaken the dedup backstop (`docs/features/dedup-consumer.md`) — a
  genuine duplicate delivery in this system is a broker resending the *exact same event*, timestamp
  included.
- **Applied directly to the shared model, not a parallel schema**: an earlier version of this feature
  kept partitioning in a standalone demo table specifically to avoid conflicting with SQLite-based
  tests, which cannot autoincrement a composite primary key at all. That constraint no longer applies —
  this project's test suite now runs exclusively against real Postgres (see
  `docs/DECISIONS.md` "Real Postgres/Redis in tests, not SQLite/fakeredis"), so there's no second
  dialect to keep compatible with, and the partitioned schema is simply *the* schema every test already
  exercises.
- **DEFAULT partition always created**: without one, an insert whose `timestamp` doesn't fall in any
  explicit partition's range is rejected outright by Postgres.

## Python version notes

No version-gated syntax; targets the full 3.11–3.14 range.

## Testing plan

- Verified `postgresql_partition_by` compiles to the expected DDL and that DDL parameter binding
  doesn't work for `PARTITION OF ... FOR VALUES` (`there is no parameter $1` — caught against a live
  Postgres, fixed by inlining date literals) before trusting the module.
- Verified end to end against the real `postgres:18.4-alpine` container: schema init creates the
  expected partitions (`trades_2026_07`, `trades_2026_08`, `trades_default`), a current-timestamp
  insert routes to the current month's partition, an out-of-range (2020) timestamp routes to
  `trades_default`, confirmed via `tableoid::regclass`.
- No dedicated unit test file — this is exercised implicitly by every test that uses the shared
  `pg_engine` fixture (`tests/conftest.py`), since schema init always runs `ensure_partitions`.
